7Software

All new code lives in this fork under openpilot/selfdrive/hud/ and reuses openpilot's messaging, Params and UI framework. The existing UI is left as it is, so the comma four's own screen is unchanged. The new code falls into five processes, a projection chain, and a set of bring-up facts that were checked in the source.

7.1 New processes on the Jetson

Each job is a separate process. A fault in one does not take down the others, and each can be tested alone on the bench. The plan does not yet state a restart policy for a crashed process; that is an open item for Phase 1.

The two new services matter for the rest of the stack. hudEyePose is the only input that changes the projection on every frame, and hudDetections is the only input that carries something openpilot does not produce. Both are published from the Jetson, and neither is consumed by openpilot, so neither can change how the car is driven.

7.2 The projection, concretely

Today's UI computes video_transform @ K_cam @ view_from_calib and passes the result to ModelRenderer.set_transform. That maps the model's points onto the camera's video. The HUD replaces it with a chain that maps the same points onto the virtual image:

D @ K_eye @ view_from_eye @ eye_from_car
  • eye_from_car is the rigid transform from the calibrated model frame (x forward, y right, z down, origin at the road camera) to the eye. The head tracker's live offset is added here. Points on the ground still need the camera height, extrinsicsCalibration.height[0], with a default of 1.22 m, added in z. model_renderer.py does this today.
  • K_eye is the pinhole for the virtual display plane, from the calibration in section 6.9.
  • D is the pre-distortion mesh. It is applied as a render-to-texture pass, not folded into the matrix, because a mesh cannot be expressed as a single matrix.

Figure 18 in the optics chapter shows the same chain as boxes with the measurement method for each step. The age compensation of section 4.6 is applied to the points before this chain runs, so the prediction and the projection are separate, testable steps.

7.3 Drawing limits

MIN_DRAW_DISTANCE rises from 10 m to the bottom edge of the virtual window. Points nearer than that would project below the window, where the hood hides the road, so they are not drawn. This keeps the path from appearing to float over the bonnet.

7.4 Bring-up details already known

The following facts were read in the source. Each one changes what must be built first.

  • Full screen on a chosen output. system/ui/lib/application.py never calls raylib's full-screen or monitor functions. hudd adds set_window_monitor and toggle_fullscreen, and sets BIG=1, FPS=60 and ENABLE_VSYNC=1. Vsync stops tearing in the mirror image.
  • GL version. The shaders are GLES 3.0 or GL 3.3 core. The Jetson's driver supports both, but this is untested in this tree. A sensible first test is a full-resolution triangle, which separates GL problems from renderer problems.
  • Params and state the UI reads locally. ui_state.py reads IsMetric, ExperimentalMode and CarParamsPersistent from local Params, and derives started from deviceState and pandaStates. hudd receives deviceState and pandaStates through the bridge and copies the few Params it needs once at start, so the HUD agrees with the comma four about units and engagement.
  • Jetson runtime. JetPack 6.2 gives Ubuntu 22.04 and a modern glibc. That should let openpilot's manylinux_2_28 aarch64 wheels and the uv-managed Python 3.12 install natively. Building the UI alone does not need LLVM. unverified until installed on the device.
  • Power mode. Flash with Seeed's guide and keep nvpmodel at MAXN, not MAXN SUPER, which Seeed says this carrier cannot cool.

7.5 Bench-first development

Nothing in the software plan waits for a car. Every stage can run on a mini PC with recorded data. tools/replay/replay --demo publishes a real route's modelV2, radarState, carState and calibration as msgq. A bridge on the mini PC republishes them to the Jetson exactly as the comma four will. tools/clip renders the HUD to MP4 for regression checks. tools/sim with MetaDrive exercises engagement-state changes. The Stage 0 rig sits on the same desk.

Two points keep the bench honest. Replayed data has no live latency, so the bench tests timing only through the bridge and the render loop; the photodiode test in section 10 is the only measure of the real pipeline. And the mini PC is an x86 machine, so it tests logic but not the Jetson's GL driver or its power limits. Bench success is necessary for the Phase 2 gate, not sufficient.
