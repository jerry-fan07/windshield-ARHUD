5Self-driving integration

5.1 Why openpilot

openpilot is chosen over other open driving stacks for three reasons. It is the only one with a maintained list of supported cars. It enforces a hardware safety model in panda firmware. And its message bus can be tapped by a second machine without changing the driving code. Alternatives such as Autoware or a research stack would need a drive-by-wire interface built from scratch, and they would carry none of the safety model. The HUD depends on the bus, so the choice of stack determines how much of the HUD can be built on existing code.

5.2 Track A, the critical path: the comma four drives

Track A puts a comma four and a car harness in a supported car and runs the fork's branch on it, so the HUD and the driving computer share one source tree. The driver engages openpilot normally. The HUD mirrors the engagement state. Nothing about openpilot's driving behaviour is modified for the HUD; the HUD only adds a subscriber.

The changes on the comma four are small and are listed below. Each one is a place the plan is most likely to need an adjustment once the hardware is in hand.

5.3 Track B, research: openpilot on the Jetson

Track B is kept alive for a practical reason. JetPack 6.2 (CUDA 12.6, TensorRT 10.3) removes the TensorRT 8.5 parser failure found on 2026-10-07, when the driving model could not be parsed on the Jetson's JetPack 5.1.3 install. Track B is worth doing only if it lets the Jetson run the whole driving stack, not just the HUD. The blockers below were each verified in this checkout.

The first blocker is the one that decides Track B. Without a CUDA build of the model, nothing else matters, because the driving model is the part that must run for openpilot to drive. The plan's first milestone is therefore narrow: modeld running on CUDA against a replayed route, with outputs matching the Qualcomm build.

Open before Track B starts

The plan does not define "matching". Before the parity test begins, set a numeric tolerance for the model's outputs (path points, lane-line probabilities and lead distances) and the replay route it is measured on. Without a tolerance, the go/no-go decision has no criterion and can be argued either way.

Go/no-go happens after Track A is driving. Track B does not block the HUD: if it fails, the Jetson remains a HUD computer, and the design does not change. That is the reason Track B sits after week 12 on the schedule (section 9).
